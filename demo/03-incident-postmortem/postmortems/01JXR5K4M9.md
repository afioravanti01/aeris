## Root cause

The saga failed at the apply_manifest step, which attempted to create a Deployment resource via the Kubernetes API server at api.k8s.acme.com. All three POST requests to /apis/apps/v1/namespaces/prod-eu-1/deployments returned HTTP 502 Bad Gateway, indicating that the Kubernetes API server itself or an intermediary proxy (ingress, load balancer) in the prod-eu-1 cluster was unavailable or overloaded at the time of the deployment. The upstream signal is unambiguous: a consistent 502 across all retry attempts with an empty response body (resp_hash sha256:0000…) confirms the API server was not reachable, not that the request was malformed. The prior steps (reserve and build_image) completed successfully, so the failure is isolated to cluster-side infrastructure availability in prod-eu-1 at 08:30:14 UTC.

## Mitigation

1. **Immediate remediation**: Investigate the health of the prod-eu-1 Kubernetes API server and any intermediate load balancer or ingress proxy at the time of the incident (08:30:14 UTC). Check control-plane logs, cloud provider status, and network metrics for that window. Once the API server is confirmed healthy, re-trigger the deploy_release saga — the idempotency keys for reserve (3a91…b07c) and build_image (4f12…aa90) ensure the completed steps will not be duplicated.
2. **Follow-up verification**: After re-deployment succeeds, confirm that the Deployment resource for acme/api:v2.4.0 is correctly applied in prod-eu-1 and that the rollout reaches a Ready state. Cross-check that the rolled-back image (acme/api:v2.4.0) was fully removed from the registry by the undo_build_image step before the re-push.
3. **Retry strategy hardening**: The three retry attempts in apply_manifest spanned only 70 ms (14.190–14.240), indicating zero back-off. Replace the current fixed-interval retry with exponential back-off (e.g., 1 s, 4 s, 16 s) and increase the maximum attempt count for transient infrastructure errors. This prevents a brief API-server blip from immediately triggering a full saga rollback.
4. **Pre-flight health check**: Add a lightweight preflight step before apply_manifest that performs a read-only GET against the target cluster API server (e.g., GET /healthz or GET /apis/apps/v1). If this check fails, the saga should halt early — before building and pushing the image — avoiding unnecessary registry churn and rollback cost.
5. **Structural alerting for control-plane availability**: Instrument the prod-eu-1 cluster API server with an availability SLO alert (e.g., error rate > 1% over 5 minutes triggers a PagerDuty page). This ensures on-call engineers are notified of API-server degradation proactively, before automated deployment pipelines encounter it.
