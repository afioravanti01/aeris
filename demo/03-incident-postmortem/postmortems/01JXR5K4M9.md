## Root cause

The saga failed at the apply_manifest step, which attempted to register the deployment with the Kubernetes API server in the prod-eu-1 namespace. All three POST requests to api.k8s.acme.com returned HTTP 502 Bad Gateway, indicating the Kubernetes API server or an intervening load balancer was unavailable or overloaded at the time of the deploy. The upstream signal is unambiguous: error kind "net", host "api.k8s.acme.com", consistent 502 responses with an empty response body (resp_hash sha256:0000…) across all retry attempts, suggesting a gateway-level failure rather than an application-level rejection.

## Mitigation

1. **Immediate remediation**: Investigate the state of the Kubernetes API server and its load balancer in prod-eu-1 at the time of failure (08:30:14 UTC on 2026-05-24). Review control-plane logs, ingress controller logs, and cloud provider health dashboards to determine whether the 502s were caused by an overloaded API server, a misconfigured or restarted load balancer, or a transient network partition. Restore the API server to a healthy state before rescheduling the deploy.
2. **Follow-up verification**: Once the API server is confirmed healthy, rerun the deploy_release saga for v2.4.0 and verify that the apply_manifest step completes with a 2xx response and that the deployment reaches the expected ready state in prod-eu-1. Confirm via kubectl that the rollout succeeded and no lingering partial state exists from the failed attempt.
3. **Improve retry strategy**: The three retry attempts were issued within 70 ms of each other (14.190–14.240), offering no meaningful recovery window for a gateway-level fault. Replace the tight fixed-interval retry loop in apply_manifest with exponential backoff (e.g., initial delay 2 s, multiplier 2, cap 30 s) and increase the maximum attempt count to at least 5 for transient network errors targeting the Kubernetes API.
4. **Add a pre-flight health check**: Introduce a preflight step at the start of the saga (before reserve) that performs a lightweight read against api.k8s.acme.com (e.g., GET /healthz or GET /apis) and fails fast if the API server is unreachable. This prevents unnecessary work—image build, registry push, slot reservation—when the target control plane is already degraded.
5. **Establish API server availability alerting**: Add a synthetic probe on api.k8s.acme.com/healthz with a sub-minute check interval and route alerts to the on-call channel. This ensures that control-plane degradation is detected and actioned independently of deploy failures, reducing the window in which the cluster is silently unhealthy.
