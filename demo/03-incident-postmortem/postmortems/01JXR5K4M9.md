## Root cause

The saga failed at the apply_manifest step, which attempted to POST the v2.4.0 deployment manifest to the Kubernetes API server at api.k8s.acme.com in namespace prod-eu-1. All three retry attempts received HTTP 502 Bad Gateway responses, indicating the Kubernetes API server (or an ingress/proxy in front of it) was itself unavailable or overloaded at the time of the call. The upstream signal was a consistent HTTP 502 with an empty response body (resp_hash sha256:0000…) across all attempts, classified as error kind "net", which triggered the saga compensator to roll back both build_image and reserve successfully.

## Mitigation

1. (Immediate remediation) Investigate the health of api.k8s.acme.com and its ingress/proxy layer at the time of the incident (08:30 UTC 2026-05-24). Check control-plane component logs (kube-apiserver, etcd, load balancer access logs) for the prod-eu-1 cluster to identify whether the 502s were caused by an overloaded API server, a proxy misconfiguration, or a transient network partition. Restore the cluster to a healthy state before re-attempting the v2.4.0 deployment.
2. (Follow-up verification) Re-run the deploy_release saga for v2.4.0 after confirming API server health. Verify that the apply_manifest step succeeds and that the deployed image matches the pushed digest (acme/api:v2.4.0). Confirm rollout status in prod-eu-1 via kubectl rollout status and cross-check with the release reservation endpoint.
3. (Retry hardening) Increase the inter-attempt backoff in the apply_manifest retry policy (currently all three attempts fired within 70 ms, providing no recovery time). Replace the tight fixed-interval retry with exponential backoff and a longer total window (e.g., 3 attempts over 30 s) so transient API server blips can resolve before the step is declared failed.
4. (Pre-flight gate) Add a Kubernetes API server health check as a dedicated preflight step before apply_manifest. The step should issue a lightweight GET /readyz against api.k8s.acme.com and abort the saga early with a clear diagnostic if the control plane is not ready, avoiding the cost of building and pushing an image that will never be applied.
5. (Structural observability) Instrument an alert on sustained HTTP 5xx error rates from api.k8s.acme.com so on-call engineers are notified of API server degradation before deployment sagas are attempted. Correlate saga failure events with cluster control-plane health metrics in the existing monitoring stack to reduce mean-time-to-diagnose for future recurrences.
